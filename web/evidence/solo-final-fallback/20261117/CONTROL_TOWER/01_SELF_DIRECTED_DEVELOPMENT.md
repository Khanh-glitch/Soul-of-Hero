# 01 — AUTONOMOUS DEVELOPMENT SYSTEM, NOT A GAMEPLAY LOOP
This is a process algorithm for an engineering agent, NOT a required player route. No prescribed New Game→wood→Core→boss→evac sequence, no bot-generated experience scores.

## Step A: Recover live facts
On every new execution: current Creator directive, repository branch/HEAD and dirty state, last solo source commit, 06 ledger, current Bible and approved docs, independent NPC branch HEAD/overlap. Read diff before editing; preserve any newer human work. Verify whether the purported gap is absent in SOURCE, unconnected in production, merely unverified, or superseded by newer law.

## Step B: Prioritize by SYSTEMIC VALUE
List 3–7 candidate missing causal links from the approved K1–K8/C01–C24 graph, not convenient test names. Assess:
1. Danger to save/data/UID, Core, money, geography and security.
2. Degree of player hardlock/fatal stall vs niche polish.
3. Number and importance of upstream sources/downstream consumers improved by the change.
4. New meaningful alternatives and counterplay, not just more items/screens.
5. Economic consequences: scarcity, competing uses, travel risk, monopolies, infinite positive cycles.
6. Temporal/offline, terrain, controls, accessibility, art and memory impact.
7. Expected compatibility with future NPC source/scheduler/custody; overlap with shared code.
8. Verification confidence and cost to implement responsibly.
First fix demonstrable P0 corruption or major unplayable performance, then large common-edge gaps, then local mechanic completion, then production polish. Reprioritize as evidence changes; do not lock a rote chronological feature list.

## Step C: Create a brief impact dossier FOR A REAL SOURCE CHANGE
Record: exact canonical rule + reference; current source function/behavior; player choices available including refusal; actual material/UID/owner/source/route; input→time/cost→committed state→consumer; offscreen/reload/failure; K1–K8/C edges touched; 21 Core/Gold or economy interactions; weather/geography changes; performance and visual impact; potential exploit; NPC compatibility/port notes; tests proving causality. Keep concise in commit notes/ledger; no 50-minute analysis-only iteration. If the full effect network is unclear, inspect it before patching rather than guessing.

## Step D: Repair COMMON ENGINE LAWS
Build functionality on existing authoritative RunState, item UID/custody, source ids, K2 Map, event clock and rendering. Do not create a parallel sandbox economy, second timebase, unsupported biome or universal spawn helper.
For every significant patch: physical source or legitimate initial state → legal player input / interaction → exact time/resource/debit/commit receipt → observable downstream state → save/restart → blocked case and exploit resistance. Test old saves and cross-run erasure.
Prefer coherent source patches with independent fast focused tests and a real composed game affordance. Commit production code; document what NOT yet proven. Then select next gap. No intentional test-only milestone when critical gameplay remains absent.

## Step E: Analyze SIDE EFFECTS, not just the local fix
Mandatory counterfactuals: What if source empty? Door locked? Wrong floor? Vendor stock consumed? Player moves item mid-queue, leaves POI, goes offline, dies, restarts, uses another vehicle, never obtains Core, never builds a house, sees a rare item early? Which old system loses its strategic value if this one becomes cheaper/faster? Which mechanics share a material/timer and can duplicate under simultaneous actions? How does the renderer scale with 157 art cells, 738 chest sources and non-NPC world? How would HumanWorld later read this mutation? All real issues need source fixes, not checkbox exceptions.

## Step F: Validate technically, then CONTINUE
Run targeted invariant/negative/property/state-machine tests, app/test TS, appropriate build, legacy save and UI technical checks. Unit fixtures may force states to reproduce edge conditions, but do NOT count as natural player agency. Browser tooling may check clicking/movement/input/collision/rendering, not fun. Human/Creator ultimately judges feel.
Do not repeatedly run unchanged full regression, or 336h endurance, to spend a development turn. Small controlled probes → hotspot hypothesis → source correction → measured follow-up → final exhaustive gate. Never hide defects by raising timeouts, deleting sources, reducing actors/graphics, skipping K8 or labeling inherited assertions acceptable.
Correct failures and continue without waiting for assistant or Creator to sign each internal task. Creator consultation only for genuine new product scope/law, asset approval or subjective release; while one choice remains open, implement unrelated approved features.

## Failure / interruption handling
Source bug: own repair, durable commit, negative case. Missing world source/access: inspect actual authored Map and appropriate K3 source, no invented stock, implement only approved change. Conflicting Creator decisions: quote both exactly, preserve latest, ask narrow decision only if impossible to resolve, continue independent work. Inaccessible backend/hardware: document reproducible constraints, never fake globally VERIFIED rank or native proof. Historical v5/v6 ambiguity: verify original archive/mode before claiming quantitative LI fidelity, not random invented numbers.
A repeatable coding-agent session terminates due to platform limits even if project incomplete. Always write handoff with exact SHA, actual source change, remaining blockers, first next function, and tests; the next invocation should proceed with no fresh briefing. Do not promise it runs in the background.

## Source vs quality gate
SPEC_ONLY ≠ CODE_EXISTS ≠ ENGINEERING_VERIFIED ≠ WEB_COMPOSED ≠ NATIVE_COMPOSED ≠ HUMAN_S4 ≠ LONGITUDINAL_S5. Only Creator/human legitimately accepts overall experience. If only subjective choice remains, supply review-ready current build and precise human questions, not an AI declaration of completion.

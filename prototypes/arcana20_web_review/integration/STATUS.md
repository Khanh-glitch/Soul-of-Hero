## Quality and measurement

An isolated review session-only cadence selector offers High (60 Hz source ticks), Balance (up to 30 Hz) and Performance (up to 20 Hz) outside protected event windows. This is **not an approved or shippable set of quality tiers**. Reduced cadence changes visual motion, and switching/overlapping casts and hardware profiling still require verification. In limited fixed-step samples, the High tick input matched raw-seconds output for B, C and D source players. The source-only #20 synthetic CPU benchmark rendered 60/30/20 samples with medians 228.7/115.3/78.4 ms and identical final fields; it does not measure game FPS or visual equivalence.

D19 High remains unbatched by default; experimental Balance and Performance use sprite-only batching, with `arcanaDBatch=none` restoring the unbatched path and `arcanaDBatch=sprites` opting High in. The candidate produced byte-identical outputs in ten paired SwiftShader samples and reduced one sample from 273 to 102 draw calls (raster/readback median 26.5 to 19.4 ms). All-type batching differed at 4–5 pixels by at most 1/255 and is not the default. This is not hardware performance evidence. A prior #20 SwiftShader run had an approximately 5.9-second composite stall that did not recur in later runs; its cause is unproven.

## Latest performance research and experiments

- External guidance consulted: MDN WebGL best practices (https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) recommends measuring DOM texture uploads, avoiding blocking GPU queries, and preallocating textures where appropriate; Chromium's canvas/WebGL discussion (https://issues.chromium.org/issues/41311312) explains why direct canvas upload may enable GPU copies and explicit readback can defeat those optimizations. These are hypotheses, not proof of the cause of our stalls.
- The C compositor uploads the union of current and previously marked influence bounds and clears stale data; it still samples the whole real world and all marked field texels. Its GPU output uses an influence-bounded scissor, while scalar fallback deliberately retains the full source window for displaced reads. Compared with the preserved immediately previous packed GPU path, 18 interleaved/moving/shrinking/empty stress cases and 42 transformed effect samples were byte-identical on SwiftShader; the previous older float-texture reference differed by 1/255 in one newly sampled #07 edge pixel, so it is not claimed bit-identical for all cases. Small fixed-frame paired medians improved by ~0.2–1.9ms in this software sample, not a device FPS claim.
- A natural #20 High sample after both changes reached 6.8s source time with median frame interval 60.2ms, p95 140.3ms and max 3.29s. Another intrusive profiling run measured an 8.97s first GPU-constructor stall; instrumented numbers are not directly comparable to baseline. Deferred WebGL work and software context creation remain unresolved, so these samples do not establish the cause or readiness.
- #19 sprite-only batches matched unbatched raster output for 294 alternating source ticks on SwiftShader. High stays unbatched; Balance and Performance now select the sampled sprite optimization, with a restore override. A natural-time Balance sample still had median 86.1ms, p95 117.6ms and max 4.3s, and it cannot establish a hardware benefit or source-faithful D19 A.

- Browser context limits motivated reusing one A, one C and one C-post compositor per viewport size across sequential effects, rather than allocating a separate WebGL context for every skill family. The same source/revision invalidation remains inside the C compositor. Eleven A/C interleaving checks, including A 416×234 and 624×352 source switches and C rewinds, matched separately owned contexts byte-for-byte on SwiftShader. Four overlapping real inventory casts (#01/#16/#18/#20) used two WebGL contexts in the observed interval, all spent a charge and had no page exceptions; the fixture jumped the source clock and is not a visual or FPS acceptance test. Forcing C context loss produced the expected scalar-fallback warning and the cast still spent its charge; A/C/post compositors explicitly report context loss. Recovery to GPU, complete overlap/depth and cross-browser/device coverage are still open.
- Khronos's `KHR_parallel_shader_compile` specification (https://registry.khronos.org/webgl/extensions/KHR_parallel_shader_compile/) describes nonblocking completion polling, while MDN notes link/status queries and DOM uploads can block. No shader prewarm or asynchronous initialization is claimed here: the 8.97s constructor sample could include context/driver work and needs further isolation.

## Fresh #20 stall investigation

- Optional `ARCANA_GPU_INIT_PROFILE=1` measures synchronous WebGL context/shader queries; `ARCANA_LONGTASK_PROFILE=1` records browser Long Task entries and rAF gap start times. C stage/post diagnostics also expose bounded per-frame timings. These are instrumentation, not production telemetry, and individual calls may defer work.
- Three short fresh-server SwiftShader #20 samples measured C initialization at 9.8, 9.4 and 25.2 ms; the previous 8.97-second constructor observation did not recur. In a natural-time run to 6.8 seconds, the maximum rAF gap was 4.34 seconds while no Long Task entry was recorded within that gap; the largest C world-composite call was 14.9 ms and C post call was 289.8 ms. Browser scheduling, GPU work, page instrumentation limitations or other causes remain possible; these observations do not establish a root cause or a solution.
- Two light-only C shader fast-path experiments were reverted: they preserved sampled pixels but were slower on paired SwiftShader tests. An A persistent-texture experiment was also reverted: output matched sampled frames but median differences versus reallocation were mixed (29.2→30.1, 28.7→28.5, 30.9→30.5 and 29.0→28.8 ms), so a meaningful benefit was not demonstrated. All timings are synthetic and not target-device GPU measurements.
- Natural-time High #17/#19 samples using the same Long Task observer reached their selected beats with no page exceptions and charge 3→2. On SwiftShader their median/p95/max rAF intervals were 63.4/177.9/3183.8 ms and 86.2/112.2/4517.1 ms respectively; neither maximum gap overlapped a reported Long Task entry. This observer does not prove that rendering, browser scheduling, or driver work was non-blocking, and these measurements do not validate either visual quality or performance on a real GPU.

### D19 event and bloom investigation (follow-up)

The normal D19 diagnostic remains unchanged by default. For investigation only, `?arcana19Post=ldr` enables a bounded-LDR, pre-HUD additive approximation of the source's one-tick flash and carries the original five burst-filament commands plus that flash across at most three skipped fixed ticks. It does not change the source state, source command list, simulation, or the ordinary default path; long jumps do not replay the event. The canvas state is restored afterward. A synthetic browser test and one real UI cast observed the opt-in flash where the default emitted none, but this is not P0 post/HDR, shake, actor-depth, motion, or art acceptance. The source raster still requires WebGL2.

A temporary two-scale source-weight bloom-difference experiment used the real live pre/post-D world, not synthetic scenery; it did **not** restore the central star or eliminate the stripes and is not retained. On this Linux headless SwiftShader environment, one 1.5-second D19 Performance sample had median cast rAF intervals of 127.1ms without the trial versus 180.8ms with it (baselines 87.9ms and 69.8ms respectively; p95 252.7ms versus 292ms). These are highly variable single samples, not target-GPU measurements. The original D post expects a 480×270 scene and has HDR/color-space/depth requirements the web pass does not satisfy. A source-faithful live scene/post integration and real-device profiling remain unresolved; the trial should not be presented as a fix.

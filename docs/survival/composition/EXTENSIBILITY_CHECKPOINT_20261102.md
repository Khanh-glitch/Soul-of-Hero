## Extension audit and decision

1. **Reuse existing catalog/adapter (preferred wherever sufficient).** `data/survival/items/items.json`, `sources.json`, `world_source_bindings.v3.json`, recipes/research/stations and the A3 queue are data-driven in part. Session `available_recipes` and `queue_recipe` use catalog entries rather than a per-recipe UI branch; queue/collection still enforce station identity/reach and the canonical adapter. SaveService pins source hashes and `a0_v5_source_pins.gd` pins the owner data. Thus changing a catalog is **not** presently a data-only shipping change: it needs an A3 owner adoption/pin review; QA-only catalogs must be isolated without weakening the production pin.
2. **Thin typed guard only where a demonstrated gap exists (chosen checkpoint).** A3 `_load_bindings` indexes `loaded[binding_id] = ...` without rejecting duplicate IDs, so a future owner-approved/pinned document can silently overwrite an earlier physical binding. `source_binding_guard.gd` checks the current v3 document/schema and duplicate IDs before the existing session configures A3. It neither owns data nor validates physical authority; A3 and its 13-field host remain mandatory. This prevents ambiguity; it does **not** implement the physical source seam. Owner A0/A3 review required.
3. **New universal entity/event framework (rejected).** Would duplicate existing SaveService, A3 queue/custody and A1 authority without fixing the missing physical binding. New behavior still requires an owner-approved typed handler and adversarial tests; new rules require creator approval.

Three expansion blockers, not an excuse to rewrite: `chapter1_overworld.gd` `AUTHORED_SOURCE_KINDS` maps authored material keys in code; `economy_service.gd` `TOOL_USE_RESOURCE_KINDS` maps specific item IDs to resource kinds inside the **pinned** A3 script; `survival_build_system.gd` `BUILD_SLOTS` and overworld shortcut handling explicitly enumerate build IDs. Some typed handlers and binding checks are intentional, not inherently defects. Do not replace any owner table without a demonstrable owner-compatible path and tests. New recipe using the existing queue is plausibly data-driven once A3 approves/adopts catalog bytes; no QA variant was executed here. New authored physical sources **cannot yet be claimed data-only** through A3's 13-field custody.

## Critical seam / no bypass

It does not call `bind_authored_source_host` anywhere. `SurvivalResourceNode.interact` instead uses the legacy A0 harvest path (and can fall back to bare-hand harvest). That path has its own SaveService commit and node state, but is **not** the 13-field A1/A3 authenticated source pipeline. `world_source_bindings.v3.json` describes five A3 source-action bindings, including three non-POI roadside instances with a waystation context; A1 natural `resource_nodes_near` returns separate resource node IDs/material keys. They must not be equated just by label or a UI coordinate.

A0 and A3 pins cannot be silently changed. Guard test fixtures are *only* malformed definition inputs, not pretend authoritative receipts.

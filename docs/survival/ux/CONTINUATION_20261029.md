## Modal interface — proposal only

Both UI scenes start hidden, expose `is_modal_active()`, emit `modal_state_changed(bool)` on `open_*`/`close_*`, and emit `closed`. Repeated explicit open or close is idempotent; focus is restored on explicit close. This is **not** an authoritative gameplay input gate. A0 must decide lifecycle, aggregate nested modals, account for parent hiding/freed controls, and block polled gameplay actions including release-frame ordering. Do not wire until A0 proves in the real production overworld: build active + journal click → no placement/debit; close + world click → exactly one paid placement; cancel closes modal without accidental retreat; combat does not leak. Signal state tracks explicit calls, not all possible parent visibility or tree destruction. UI cannot enforce gameplay invariants.

## Desk contract v0 — UI-only DTO, NOT agreed producer schema

`set_snapshot(Dictionary)` deep-copies a host-prepared snapshot. Host must pre-filter all private information; `revealed: true` additionally filters recipe/place/hazard lists in the view. A false/missing flag suppresses display, search and map points, but **not** data exposure in memory: do not send undiscovered records to the client. Producers must supply honest visible metadata, quantity, capacity/eligibility and sanitized strings. All IDs are host-provided exact stable IDs.

- `revision`: opaque producer-owned revision forwarded with every request; no revision comparison or integrity validation occurs inside the UI.
- `recipes`: `{id, name, revealed, found, learned, station, ingredients:[{name,have,need,source?}], can_craft?, can_research?, blocked_reason?}`. Search includes *visible* ingredient names. `found` means blueprint known/found, not that a physical Core grants permanent formula. Action buttons default disabled unless explicitly allowed by producer. UI does not determine affordability or learn state.
- `bag`, `chest`: `[{id,name,count}]`, `container_id`, `transfer_enabled`. Snapshot `id` for the A0 transfer endpoint must be the **item ID**, not inventory stack key. Existing `SurvivalService.transfer_to_container` / `transfer_from_container` use item IDs, quantities and transaction keys. `Adapter.storage` projects `SaveService.inventory_totals()` and `SurvivalService.container_contents()` plus catalog names; it returns `transfer_enabled=false` regardless of contents and doesn't prove an existing/interactable chest. Host must check access/capacity, generate unique transaction keys and route/revalidate atomically. UI count/spinner are hints, never authorization. The earlier fixture uses a synthetic `oak_wood#1` to prove opaque IDs and is NOT an actual A0 API example.
- `places`: `[{id,name,revealed,position:Vector2,route,hazard,activity}]`; normalized [0,1] schematic coordinates. Markers are a deliberately simple clickable schematic, not A1's real geographic map, and omit invalid/undiscovered positions. List enables keyboard selection. No world geography, route state or progression inferred.
- `hazards`: `[{name,revealed,protection,preparation}]`; `recovery`: `{anchor,bed_status,bag_status,preserved,dropped}`. Text is supplied by the owner; absent data says unknown. No bed/death/hazard state or recovery transactions are implemented.
- `cores`: `[{id,name,charges,max_charges,condition,equipped,blueprint_found,learned,can_equip}]`. IDs identify physical instances, not skill types. A3 must define real representation; A4 owns source-faithful Gold/VFX. Invalid/depleted counts are labelled and equip requests disabled; whether spent cores can equip is a provisional UX assumption for A3 to confirm. No skill effects changed.

`request_action(action, target_id, payload)` emits `craft`, `research`, `transfer`, or `equip_core`; transfer payload carries `{direction,container_id,amount,revision}`. The UI does not mutate any stock or knowledge or claim action success. It disables new requests while pending; `set_snapshot` does not clear pending. Host must resolve each attempt by calling `resolve_request(message)`, refresh authoritative data and prevent duplicate/late/replayed requests itself. The local pending flag is **not** a transactional idempotency guarantee. UI cannot guarantee correct status if the host supplies a stale snapshot, spoofed capability, unknown ID, or silently drops a callback. Never accept these DTO flags as a substitute for A0/A3 transactional validation.

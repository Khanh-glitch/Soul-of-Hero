**Status: OFFLINE FIXTURE / HOLD PRODUCTION INTEGRATION.** This is an A6-owned UI proposal, not an approved A0/A3 service contract or gameplay implementation. `expedition_workspace.tscn` composes the Journal/Satchel and the five-tab Desk. A single host-supplied snapshot populates the satchel, placement, field notes and planner; the UI does not execute inventory, research, crafting, respawn or Core transactions. `tests/survival/ui/fixture_host_v1.gd` is explicitly fake and exists only to exercise the interface. ## Mandatory input boundary

`modal_state_changed(bool)` reports the aggregate explicit workspace open/close; switching views does not pulse false. `is_modal_active()` and `closed` are provided. These signals **do not block polled gameplay input**. A0 owns an actual gameplay-input gate, stacked/nested modal lifetime, parent hide/free, action-release ordering and real native regressions. Before integration A0 must verify at least: modal click cannot place/debit while build input is active; after close one world click produces exactly one paid placement; cancel does not cause retreat; combat input does not leak. The fixture checks only GUI routing to an `_unhandled_input` observer, not `Input.is_action_just_pressed` in `_process`. Explicit calls, not arbitrary parent visibility/tree destruction, drive the signal. Do not attach this scene to production until A0 approves and verifies its gate.

## V1 snapshot

`workspace.apply_snapshot(snapshot) -> bool` deep-copies via Desk and then projects to Journal. Required `schema: "soh.ui.snapshot.v1"` and nonnegative integer `sequence` are producer-owned and monotonic for the entire workspace instance; lower or same-sequence/different-content snapshots are rejected. Repeated identical snapshots are accepted. `revision` is opaque and forwarded to the host, not ordered by UI. Restart/reset of the sequence requires a new workspace instance or an explicitly agreed epoch protocol; none exists here. Sequence is a view-stream version: every change in the supplied view must advance it. This does not make data trustworthy, validate a gameplay revision, or authenticate a sender.

Additional fields are provisional and optional:

- `satchel`: physical stack rows `{id, stack_key, name, count, kind, condition?, charges?, max_charges?}`. When absent, aggregated `bag` is displayed with `id` as fallback key. `bag` and `chest` contain aggregated item-ID rows for the current A0 transfer endpoint, not stack keys; `container_id`, `transfer_enabled` and optional `capacity_status` come from host. A local name filter applies to the displayed source container; it does not query undisclosed inventory. `Adapter.bag` and `Adapter.storage` are read-only projections; the latter never authorizes transfers or proves chest access.
- `placement`: `{name,status,costs:[{name,have,required,missing,sources:[]}]}` from a real host projection where available. `field_entries`: `[{revealed:true,title,text}]`; no false/missing-revealed entries are displayed. Snapshot producers must filter undiscovered content **before sending it**: the defensive UI filter does not remove private data already in memory.
- `recipes`: `{id,name,revealed,found,learned,station,station_status?,queue_status?,ingredients:[{name,have,need,source?}],can_craft?,can_research?,blocked_reason?,research_warning?}`. Search includes only revealed recipe and ingredient names; its query is retained across refreshes. Found is distinct from learned; host supplies all authorization, prerequisite and known-source state. Research asks for confirmation and rechecks latest capability before emitting. A stale host can still reject atomically.
- `places`: revealed records with host-supplied normalized `Vector2` position and optional route, threat, activity, status and preparation. The map is a schematic, not A1 geography. Wheel zoom, right-drag pan, +/-/reset controls and a keyboard-selectable list are provided. Out-of-bounds/invalid and unrevealed points are not drawn or hit-tested.
- `recovery`, revealed `hazards`, and optional `respawns`: status and available/reason strings supplied by host; a selectable respawn emits an intent. No actual death, hazard, bed or recovery effect is applied by the UI.
- `cores`: physical instance IDs, charges/maximum, condition, equipped, found/learned and `can_equip`; optional `readiness` is informational. Depleted/invalid charges disable this proposed equip request. The equipped Core, permanent formula and Gold/skill readiness are separate. Actual A3 representation and A4 Gold behavior remain unverified.

## V1 intent and response

`request_action(action, target_id, payload)` emits `craft`, `research`, `transfer`, `equip_core` or `select_respawn`; payload includes `schema: "soh.ui.intent.v1"`, random per-instance client nonce + serial `request_id`, `sequence`, opaque `revision`, and action-specific fields. Transfer includes `direction`, `container_id`, positive `amount`, item ID target. UI blocks new logical actions while one is pending; switching tabs/views or receiving a snapshot does not release it. A manual retry re-emits **the exact same ID and payload**; it is not a new transaction. No timer assumes success or cancels a request.

Host must authenticate and revalidate all identifiers, distance/access, amounts, destination capacity, station, recipe, prerequisites, specimen/ingredients and current state; atomically apply or reject. Host must durably deduplicate by request ID *and* reject conflicting reuse with a different action/target/payload; a UI button lock or nonce is not transactional idempotency. A retry of a settled request must return the original decision with a **current** view snapshot, not execute it again. Fixture receipts are in memory only and prove none of this for production.

`workspace.apply_host_response(response) -> bool` requires `schema: "soh.ui.response.v1"`, current `request_id`, `status: "accepted" | "rejected"`, `message`, and a valid current V1 `snapshot`. Wrong IDs, invalid status/schema, stale/conflicting snapshots and replays leave the current pending request intact. On valid reply the snapshot is displayed and the pending flag clears; rejections show the host message without locally changing stock. A host that drops a response leaves the UI pending until a correlated retry/resolution. Host shutdown, reconnect, durable reconciliation, timeout UX, epoch resets and multi-client authority need owner design. Legacy planner `set_snapshot`/`resolve_request` remain only for unversioned fixture compatibility; after a V1 stream begins, they cannot overwrite it or unlock its pending intent.
